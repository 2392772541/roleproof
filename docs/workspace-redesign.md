# 从功能展示到岗位工作区

日期：2026-09-09。个人项目 v0.3。

## 触发问题

用户指出：“不像个真项目，都是在一个页面里来回跳。”代码检查发现，九个入口由一个 `view` 状态切换，没有 URL 路由；所有岗位内功能读取顶部全局岗位选择。首页展示项目说明，用户需要自己拼接操作顺序。

## 产品决策

围绕“准备一份真实职位”组织操作，长期项目证据跨职位复用，材料、核对记录和回答归属于具体职位。

| 原行为 | 新行为 | 用户得到的结果 |
| --- | --- | --- |
| 首页展示开发者项目档案 | 首页列出进行中职位及下一步任务 | 打开就能继续准备 |
| 九个平级功能入口 | 三个全局主入口，四个岗位内步骤 | 知道自己在哪份职位的哪一步 |
| 全局岗位选择 + 临时视图状态 | 地址中包含岗位 ID 与步骤 | 可刷新、返回、前进、直接打开 |
| 职位只有表格 | 五阶段看板，可修改阶段，也可切回列表 | 看清关注、准备、投递、面试和结束的分布 |
| 草稿只在页面里展示 | 核实并编辑后下载 Markdown，附证据链接 | 获得可用于后续投递的文件 |
| 根据旧公司/项目名自动重置 | 保留已有工作区，仅显式恢复会清空 | 自己录入的内容不会因升级而丢失 |

右侧网页 GPT 作为第二意见指出：四个标签仍可能成为功能拼盘；必须展示下一步，并取消全局岗位选择。这是产品复核意见，不是用户研究或外部事实证据。实际落实了任务提示、岗位上下文、来源入口、进度计数和步骤末尾导航。

## 信息架构与地址

```text
#/home                         工作台：我的机会与下一步
#/jobs                         我的职位：阶段看板 / 列表
#/jobs/:id/requirements        岗位要求：原文与人工校正
#/jobs/:id/evidence            证据核对：确认、编辑、驳回
#/jobs/:id/materials           投递材料：草稿、编辑、下载
#/jobs/:id/interview           面试复盘：回答、薄弱点、行动
#/evidence                     可复用的项目证据库
#/about                        关于项目
#/evaluation                   规则解析评测
```

选择 Hash 路由是为了让 GitHub Pages 的深链接直接可用，不需要服务端重写。技术上仍为 React 单页应用，产品上是有明确地址与岗位上下文的多个任务页面。URL 不携带私人数据；其他设备没有相同工作区时会提示找不到职位。

## 可复现验收

1. 首页录入一份职位，保存后地址包含新职位 ID。
2. 校正要求，进入证据核对；接受、修改、驳回作用于该职位。
3. 生成材料，未确认时下载不可用；编辑或确认一段后可以下载，待确认和已驳回段落不出现在文件里。
4. 进入另一职位，其材料不会继承前一个职位的正文；返回原职位仍能看到原内容。
5. 修改求职阶段，返回看板，卡片位于对应阶段；刷新后保持。
6. 在岗位内前进/后退、刷新，职位与步骤保持一致。
7. 打开不存在的职位地址，显示缺失提示，不显示默认样本冒充目标职位。
8. 390px 手机屏幕可以操作，阶段看板在容器内横向滚动，不拉宽整个页面。

验证：Oxlint、TypeScript、Vite 构建、15 条 Vitest、36 个桌面/手机 Playwright 用例通过。截图来自实际页面。

## 真实能力与未完成的研究

- 当前是规则解析与证据整理工具，没有真实模型推理、账号、后端、云同步或自动投递。
- 阶段由用户自行记录，不能证明实际投递或面试发生。
- 已确认材料是用户操作状态，不代表平台替用户验证过经历。
- 改版尚无真实求职者可用性测试，不能宣称提升准备效率或面试通过率。
- 下一轮用真实 JD 完成一次准备任务，记录中断点、耗时、误操作与下载材料的可用程度，再判断是否需要模型接入。
