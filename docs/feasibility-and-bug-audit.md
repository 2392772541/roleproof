# RoleProof 可行性与缺陷审计

> 审计日期：2026-09-04

## 1. 结论

RoleProof 的产品方向可行，最适合作为 AI 产品经理 GitHub 作品集中的主项目。它不是普通“简历润色器”，而是围绕以下可演示闭环组织产品：

```text
职位 JD → 结构化要求 → 项目证据匹配 → 人工确认 → 岗位作品集 → 面试准备与复盘 → 证据补强
```

它对面试的价值不只在于页面完整，而在于能证明候选人具备：问题定义、领域建模、AI 边界设计、可解释规则、Human-in-the-loop、数据完整性、异常处理、评测与工程交付能力。

## 2. 差异化判断

求职产品通常集中在职位追踪、ATS 关键词匹配、简历生成、自动投递或模拟面试。RoleProof 选择 Evidence-first（证据优先）：先建立可以核验的项目事实，再生成岗位表达。

应继续坚持：

- 生成内容必须引用真实 Evidence ID。
- 无证据时显示 Gap，不补写虚构经历。
- AI 建议必须允许接受、编辑和驳回。
- 人工决策必须真实约束评分、作品集和面试准备。
- 项目必须有可运行 Demo、测试、截图和决策文档。

不应退化为：

- 只有一个匹配百分比的 ATS 工具。
- 套壳聊天机器人。
- 自动批量投递器。
- 只会润色文案的简历生成器。

## 3. 本轮发现并修复的缺陷

### 3.1 非法 JSON 工作区可清空职位并导致崩溃

**复现：** 导入 `jobs: []` 的不完整工作区。

**根因：** 原导入逻辑只检查少量顶层字段，没有完整 Schema 和关系校验。

**修复：** 新增 Zod 工作区 Schema；校验字段、枚举、分数范围、重复 ID、Requirement.jobId、Interview.jobId；非法导入在任何状态写入前整体失败。

### 3.2 合法 JSON、错误结构的 localStorage 会破坏启动

**复现：** `jobs=[]`、`evidence={}` 或错误 JSON。

**修复：** `useLocalStorage` 支持 parser；每类缓存使用严格解析器，无效缓存回退演示数据；存储被禁用或写满时不抛出未处理异常。

### 3.3 空格绕过 required，产生空职位或空证据

**修复：** 公司、岗位、JD、证据核心字段全部执行 trim 后业务校验；无法解析出 Requirement 的 JD 不允许保存；权重限制在 1–10。

### 3.4 职位列表与详情分数不一致

**根因：** 列表读取保存在 Job 中的旧 score，详情实时计算。

**修复：** 所有界面和导出统一使用当前 Job × Evidence × Decision 实时计算结果。

### 3.5 证据完整度与材料数量是假数据

**修复：** 完整度改为 Verified Evidence / Evidence 总数；材料数量只统计存在真实 URL 的 GitHub、Demo、PRD、截图或报告链接。

### 3.6 Reject 只改状态，不约束下游生成

**修复：** 被驳回的 Match 强度归零，不再进入实时评分、岗位作品集和面试 Evidence；界面明确提示补充新证据。

### 3.7 “编辑后采用”原来是假编辑

**复现：** 点击后只记录 `edited`，无法改变引用的 Evidence。

**修复：** 用户可以输入要保留的 Evidence ID；系统过滤不存在的 ID，将覆盖结果写入 Decision Log；评分、作品集和面试统一使用人工编辑后的引用。

### 3.8 重新生成作品集会覆盖手工文案

**修复：** Pending 段落可以刷新；已经人工编辑、接受或驳回的段落会保留，不再静默丢失。

### 3.9 重新生成面试问题会覆盖回答与复盘

**修复：** 使用稳定的问题身份并合并旧记录；保留回答、薄弱点、下一步行动、人工状态和已确认 Evidence。

## 4. 自动化回归范围

单元测试覆盖：

- JD 结构化解析。
- Evidence ID 合法性。
- 评分和不超过 100。
- 无证据时返回显式 Gap。
- 工作区 Schema 与重复 ID。
- Requirement 与 Job 关系。
- 缓存空职位拒绝。
- Edited / Rejected 决策真实改变 Evidence 引用。

Playwright 端到端测试覆盖：

- 桌面端与 390×844 移动端完整闭环。
- 职位、证据和 Requirement 表单。
- JSON 导入导出与非法数据。
- 实时评分和真实材料指标。
- Reject 不进入下游。
- Edit 真实修改证据引用。
- 再生成不覆盖作品集与面试人工内容。
- Console Error、Page Error 与移动端横向溢出。

## 5. 面试演示建议

面试时不要只说“我做了一个求职工具”，应按以下顺序演示：

1. 输入一条真实但脱敏的 AI 产品经理 JD。
2. 展示规则解析结果，并主动指出 Rule Mode 的语义边界。
3. 人工修改 Requirement 权重或关键词。
4. 展开 Match，说明推荐理由和证据缺口。
5. Reject 一条弱匹配，展示评分和下游内容同步变化。
6. Edit 一条匹配，只保留真正相关的项目证据。
7. 生成岗位作品集并手工修订，证明再生成不会覆盖人工内容。
8. 填写面试回答和补强行动，完成证据回流闭环。
9. 打开测试和数据模型，说明如何防止虚构 Evidence 与损坏导入。

## 6. 剩余风险与下一步

- Rule Mode 主要依赖关键词，复杂 JD 的语义召回仍有限；需要脱敏中文 JD 标注集和模型 Adapter。
- 当前 Evidence 材料只保存 URL；需要附件、截图缩略图、失效链接检测和真实性审核状态。
- localStorage 适合 Demo，不适合多人和多设备；后续需要账户、数据库和权限。
- Evidence 编辑目前使用 ID 输入框，下一版应升级为可搜索、多选、可比较的证据选择器。
- 需要记录 Requirement 重解析的版本，避免人工校正和历史 Decision 无法追踪。
- 应增加可分享、可打印的岗位作品集，以及真实用户任务完成时间与采纳率评测。
