# RoleProof 产品案例复盘

## 1. 背景

AI 求职工具很容易退化成“输入 JD 和简历，生成一份更漂亮的文本”。这种方案虽然演示简单，但会带来三个产品风险：

- 岗位要求没有被拆解，用户不知道真正的能力缺口。
- 模型可能把弱相关项目包装成强相关经历。
- 生成内容缺少材料来源，面试追问时无法证明。

RoleProof 因此没有把“生成简历”作为核心，而是把“岗位要求与项目证据建立可核验连接”作为核心任务。

## 2. 目标用户

- 正在投递 AI 产品经理、Agent 产品经理和 AIGC 产品经理的中国求职者。
- 已经做过一些项目，但难以判断哪些项目适合哪个岗位的人。
- 希望使用 AI 辅助求职，但不希望 AI 编造经历的人。

## 3. 核心任务

用户选择一个岗位后，需要完成：

```text
理解岗位 → 找到证据 → 判断可信度 → 组织作品集 → 准备追问 → 补齐缺口
```

因此系统中的核心对象不是聊天消息，而是：

- Job：目标岗位。
- Requirement：从 JD 中提取并经人工校正的要求。
- Evidence：能够证明能力的项目事实。
- Match：Requirement 与 Evidence 的连接。
- Decision Log：用户对 AI 建议的人工决策。
- Portfolio Section：带 Evidence ID 的岗位作品集段落。
- Interview Record：真实回答、薄弱点和补强行动。

## 4. 关键产品决策

### 决策一：无 API Key 也必须完成闭环

第一版采用中文关键词与规则解析，保证任何面试官打开 Demo 都能操作。未来的模型能力通过 Adapter 接入，不改变核心数据协议。

### 决策二：保留原始 JD

解析结果可以编辑，但原始 JD 不被覆盖。这样用户能够随时复核结构化结果是否偏离招聘原文。

### 决策三：AI 建议不能自动成为事实

匹配建议必须经过 Accept、Edit 或 Reject。系统保存人工决策，而不是把一次模型输出直接写入最终作品集。

### 决策四：没有证据时显示 Gap

系统不通过“语言优化”掩盖能力不足。Gap 会被转化为补项目、补数据、补文档或补截图的行动。

### 决策五：所有生成段落引用 Evidence ID

Evidence ID 是作品集内容与原始项目事实之间的外键。生成后再次执行合法性检查，过滤不存在的引用。

## 5. 最小可用闭环

1. 用户录入目标岗位和 JD。
2. 系统解析 Requirement。
3. 用户人工校正 Requirement。
4. 系统根据能力、关键词和材料完整度推荐 Evidence。
5. 用户确认、编辑或拒绝匹配。
6. 系统生成带 Evidence ID 的岗位作品集。
7. 系统根据缺口生成面试问题。
8. 用户填写真实回答并记录薄弱点。
9. 薄弱点回流为证据补强任务。

## 6. 评测思路

第一阶段重点验证：

- Requirement 提取是否覆盖 JD 中的关键要求。
- 推荐 Evidence 是否与 Requirement 真实相关。
- 人工接受率和修改率。
- 作品集是否出现不存在的 Evidence ID。
- 没有证据时是否正确显示 Gap。
- 用户能否在不阅读说明书的情况下完成闭环。

详细指标见 [evaluation-plan.md](evaluation-plan.md)。

## 7. 当前边界

- 当前数据保存在浏览器本地，不提供跨设备同步。
- Rule Mode 适合稳定演示，但不能替代大模型对复杂 JD 的语义理解。
- 示例指标用于展示数据结构，不能作为真实商业效果宣传。
- 当前不直接抓取招聘平台，避免依赖登录态、反爬规则和不稳定页面。

## 8. 下一阶段

下一阶段不会先增加更多生成按钮，而会优先补充：

1. 模型 Adapter 与结构化输出校验。
2. 脱敏中文 JD 评估集。
3. 材料附件、截图和真实性状态。
4. 作品集分享和打印。
5. 解析准确率、证据采纳率和人工修改率看板。
