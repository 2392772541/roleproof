# RoleProof 产品案例复盘｜面试讲解版

## 1. 一句话介绍

RoleProof 是 Evidence-first 的 AI 求职工作台：把岗位要求连接到可以打开的项目事实，并让人工决定真实约束评分、作品集和面试准备。

## 2. 问题与选择

项目多不等于面试有说服力。岗位要求、项目事实、个人贡献、测试证据和演示地址往往分散。通用生成工具会优化措辞，却不能保证每句话都能被证明。因此我没有做普通 ChatPDF 或文案壳，而是把“可核验的证据关系”作为核心对象。

## 3. 我的真实角色

这是个人独立项目。我完成产品定义、数据模型、交互、规则引擎、React 前端、持久化、测试、文档、GitHub Actions 和 Pages 发布。我没有真实商业客户、收入或线上转化数据。

## 4. 关键产品决策

### Evidence 而不是文案

Evidence 保存项目、个人角色、真实行动、结果和材料地址。不存在的 Evidence ID 会被过滤。

### 人工审核必须改变下游

早期版本的 Reject 只是状态展示，仍可能进入评分和作品集。修复后，Reject 将强度归零；Edit 保存人工选择的合法 Evidence ID；再次生成不会覆盖人工文案和回答。

### 没证据就显示 Gap

Gap 会转成补项目、截图、指标、PRD 或降低岗位优先级的行动，不用语言包装掩盖不足。

### 先做可重复基线

MVP 使用无需 Key 的 Rule Mode，保证面试现场可运行，并为模型 Adapter 保留协议。它牺牲复杂语义能力，换取可解释、可测试和可重复。

## 5. Evaluation

评测实验室用固定合成 JD、人工类型标签和期望术语，实时计算术语覆盖、分类准确、原文可追溯和无依据新增。当前 Bad Case 是可信 AI 和人工审核语义分类不足。这些弱点被公开展示并进入 backlog，而不是隐藏。

## 6. 可核验结果

9 个产品入口、3 个真实公开项目证据、严格 Schema 与关系校验、Vitest、桌面/移动 Playwright、GitHub 仓库、Actions、Pages、PRD、AI 边界、评测与缺陷审计文档。以上是工程交付，不是商业 KPI。

## 7. 5–7 分钟面试脚本

1. **问题和真实性**：打开项目档案，说明合成数据与未验证指标。
2. **数据模型**：展示 JD 原文、Requirement 和人工校正。
3. **核心差异**：在证据矩阵演示 Accept/Edit/Reject，再进入作品集证明下游改变。
4. **评测**：打开固定集和 Bad Case，解释为什么不隐藏较低的分类准确率。
5. **工程证据**：打开 GitHub、测试、Actions 和线上页面。
6. **下一步实验**：3–5 位真实求职者任务测试、脱敏 JD 双人标注、模型 Adapter 对照。

## 8. 常见追问

### 为什么不直接接大模型？

第一版先验证 Evidence 工作流。模型必须在固定集上与可解释基线比较，不能靠 Demo 感觉替换。

### 评分是不是伪科学？

它不是录用概率，而是规则下的准备优先级；五项子分可见、可复算、可被人工决策改变。

### 怎么证明是你做的？

仓库提交、代码、测试、文档、Actions 和在线 Demo 可以交叉核验。

### 最大不足是什么？

真实用户和真实 JD 分布不足。下一步优先做用户任务测试，而不是继续堆生成按钮。
